# 跨地区时间与逾期

状态：用户已选择“改为精确截止时间”（D123），统一 UTC 保存并按用户时区显示；正式需求见 [精确截止时间与跨时区显示](../package/09-time-and-timezones.md)。下文项目业务时区、纯日期及当天结束规则为已撤回候选，保留为讨论历史，不作为现行要求。

## 用户反馈与保留规则

- 用户指出产品并非固定在某个地区或国家使用，不能将北京时间作为全球统一规则。
- 截止日期仍只精确到日期，截止当天不算逾期、次日起未完成才逾期，已完成不显示、重新打开重新判断等规则保留。
- 当前需确认的是业务日期采用谁的时区，以及实际时间如何存储和展示。

## 历史候选：项目业务时区（已撤回）

| 层面 | 待确认建议 |
| --- | --- |
| 事件时间 | 创建、更新、评论、完成、日志及通知的发生时间统一存为 UTC 时间点，由服务端产生；不同用户转换显示，不存成各自无时区的本地时间 |
| 个人显示 | 用户可设置显示时区，首次从浏览器识别后保存并允许手动更改；日志和评论等时间按个人时区展示，可查看完整时间及所用时区；改变个人时区不改变任务截止日期或逾期结果 |
| 项目业务时区 | 每个项目配置一个业务时区，创建时预填创建者个人时区并可调整，管理员维护；不按国家固定、不以服务器时区作为默认业务依据 |
| 截止日期 | 按纯日期保存，例如 2026-11-10，不把它保存为 UTC 零点时间再按个人时区转换；在任务详情或日期提示中明确该日期按项目时区解释 |
| 逾期判断 | 服务端将当前时间换算为项目当地日期，与截止日期比较；当前项目日期大于截止日期且任务未完成时为逾期。同一任务对所有成员的逾期结果一致 |
| 夏令时 | 保存 IANA 时区标识，如 America/New_York、Europe/Berlin，使用对应时区规则；不只保存 UTC 偏移，也不按固定 24 小时推导所有本地日期边界，运行环境维护时区数据 |
| 修改项目时区 | 管理员修改前提示现有任务逾期判定可能变化并确认，记录前后时区和操作人时间；截止日期文字保持原值，逾期按新项目时区重新计算；已记录 UTC 事件不重写 |

## 例子

项目时区为 America/New_York，任务截止日期为 2026-11-10：在纽约项目日期进入 2026-11-11 时，仍未完成的任务对所有成员同时显示逾期。上海或柏林用户看到的截止日期仍是 2026-11-10，并能看到它按纽约项目时区解释；操作日志则按各自个人时区显示。这里说明候选业务规则，不是在指定全球默认地区。

## 比较与取舍

- 只统一 UTC 存储可以让实际发生时间对应同一时刻，但仍须定义“截止日期当天结束”按哪个地区解释。
- 按每位查看者设备日期各自判逾期，会让同一任务在不同成员处可能出现不同状态；本方案选择项目时区统一业务含义。
- 按国家直接决定偏移不能表达全部时区及夏令时变化，业务配置使用 IANA 标识。

## 参考依据及边界

- W3C Working with Time and Timezones：区分事件时间点、当地墙钟时间与不关联具体时间点的日期值；存储和展示须保留正确语义。参考 https://www.w3.org/TR/timezone/ 。该文档属于技术指导，不是本系统已验证结论。
- IANA Time Zone Database：地域时区规则及历史、未来偏移会因夏令时或政策调整变化。参考 https://www.iana.org/time-zones 。
- RFC 5545 的 DATE 定义：纯日期值包含年、月、日，不是一个 UTC 时间点。参考 https://www.rfc-editor.org/rfc/rfc5545.html#section-3.3.4 。
- 项目统一判断、个人分别显示、时区变更的管理行为属于结合本系统提出的设计取舍，不能当作上述资料强制要求。

## 待方案确认后补齐的验收

- 跨项目当地午夜、不同成员个人时区、设备时区与项目时区不同的场景。
- 夏令时切换日、无夏令时地区及日期边界，不能只用固定 UTC 偏移模拟。
- 项目或个人时区修改、截止日期保存再读取、完成及重新打开后的逾期结果。
- 服务端判断、看板、列表、筛选和匹配数量保持一致。

## 用户追问：统一时间值再按用户时区显示

- 用户询问：“我记得时间不是可以保存一个无时区或者说叫做标准时区的值吗? 然后再根据用户的实际时区转换”。本次属于方案讨论，尚未确认项目时区或修改截止日期类型，不追加已确认决策。
- 说明：UTC 时间或 Unix 时间戳可表达同一个实际时刻，创建、更新、评论、完成等事件采用统一存储、按用户时区显示的方式；这与没有指定时区的本地日期时间不同。
- 当前任务截止字段只填写日期。一个日期本身没有给出全球唯一到期时刻；需要先确定该日期按哪个地区结束，才能推导精确的 UTC 边界。项目业务时区是候选解释方式，不是替代 UTC 事件存储。
- 另一种业务选择是允许填写精确截止日期时间，按录入时选定的时区转换为 UTC 到期时刻，各用户再转换显示；这是对现有仅日期字段的需求变更，当前未确认。
- 本次再次核对 W3C Working with Time and Timezones 及 RFC 3339（https://www.rfc-editor.org/rfc/rfc3339.html），只用于解释日期与时间点的区别，没有实施时间存储或转换代码。

## 最终选择：精确截止时间

- 用户回复“改为精确截止时间”，记为 D123。
- 截止字段从仅日期改为日期、具体时间及明确时区，解析为唯一 UTC 时间点保存，按查看者时区显示。
- 逾期改为超过截止时刻且未完成，不再等到项目或用户当地次日；无截止时间不逾期，完成及重新打开规则保留。
- 不设置项目业务时区的必做要求，旧管理员修改项目时区方案不进入正式需求。
- 录入须明确时区并处理夏令时歧义，按真实时刻排序；保留日期范围筛选便利，按查询时区换算 UTC 边界。
- 示例及时间验收需求已同步正式文件，实际转换代码与运行验收尚未执行。
