# 安装包与手动在线更新

更新日期：2026-11-09。

## 同事怎么使用

首次使用交付 ZIP，按部署指南安装 Node.js、npm 依赖和 Chromium，再运行 `npm start`。有 `DELIVERY_MANIFEST.json` 且不包含 `.git` 的交付目录会自动进入受管理启动模式；源码工作区保留开发启动方式。

点击侧栏名称下面的版本号，或“系统设置 → 检查更新”，打开同一个系统更新窗口。窗口检查 GitHub 正式发行版，显示版本、发布说明和发布页链接；有新版后点击“下载并更新”，阅读重启提示，再点击“确认更新”。

下载、校验和新版本依赖准备期间可以继续使用平台。确认安装时如果还有生成、采集、评测、跟进、经验复盘、交付、旧评测或排障导出在运行，更新会停留在“处理任务后重新检查并安装”，不强制中断任务、不自动等待到稍后安装。处理任务后再次点击安装，或取消此次更新。

进入安装后平台暂停写入和任务领取，等待所有执行进程退出，备份完整数据，再切换、检查新版本并重新连接。更新窗口关闭后操作继续；再次打开可读取持久进度。停机切换期间不能取消。成功后恢复更新前的队列配置，已有任务的未知请求仍沿用原有恢复规则。

默认更新源为 `achen-11/Kooboo-AI-Automation-Lab`。需要调整时展开窗口内的“更新源”，填写 GitHub 仓库地址或 `owner/repo`。公开仓库不需要令牌；私有仓库使用有读取权限的令牌，加密保存在本机，保存后不回显，留空保留原令牌。切换仓库不会沿用旧仓库的令牌。

尚无正式发行版、缺少更新清单、网络或权限错误时，窗口显示具体原因，不会显示“已是最新”。开发源码目录可以检查版本，在线安装按钮禁用。

## 发布人怎么交付

首次带更新能力的版本仍通过 ZIP 交付一次。旧 ZIP 用户先停止服务，备份并迁入完整实际数据目录；若更改了数据路径，按部署指南重建采集 Python 虚拟环境。之后同事始终从原安装根目录运行 `npm start`，不用再搬迁数据。

正式发布前：

1. 更新 `package.json` 与 `package-lock.json` 的版本，使用递增的正式版本号，例如 `0.4.1`；完成针对性检查并提交对应源码。
2. 为同一提交创建并推送版本标签，例如 `v0.4.1`。工作区须干净；测试快照不能作为在线更新。
3. 制作更新包。输出目录必须位于项目之外，且是该版本独立的新目录：

   ```sh
   npm run release:package -- --output /path/releases/0.4.1/automation-lab-0.4.1.zip
   ```

   生成 ZIP、`.zip.sha256` 和 `UPDATE_MANIFEST.json`。清单记录版本、提交、运行要求、采集依赖指纹、整包大小与哈希；ZIP 内的交付清单继续记录逐文件哈希。打包在临时目录构建，不携带个人数据或 `node_modules`。

4. 准备更新说明 Markdown 文件，在已经登录 `gh` 的发布机器运行：

   ```sh
   npm run release:publish -- --package /path/releases/0.4.1/automation-lab-0.4.1.zip --notes /path/release-notes.md
   ```

   发布脚本核对包哈希及远端标签提交，先创建草稿、上传三个附件，成功后才正式发布并设为 latest。不会覆盖已存在的同版本发行；中途失败保留草稿供维护者检查。也可以手动创建草稿并上传这三个附件，确认完整后发布。不要把 GitHub 自动生成的源码归档作为更新包。

首次交付可直接使用同一 ZIP。依赖仍在接收端联网安装；更新器会代为安装新版本锁定的 npm 依赖及匹配 Chromium，无需同事手动执行安装命令。Node / Python 本体升级仍由同事安装。第一版只接入 GitHub；Gitee 未接入。

## 目录与恢复

初始交付目录是固定安装根目录，保留原启动器及其依赖。后续版本放在 `releases/<version-transaction>/`，`.updates/current.json` 指向实际运行版本，`.updates/state.json` 记录更新事务。启动器协议当前为 1；要求更高协议的更新会提示使用新的首次安装包。

原根目录的 `.data/` 保持不动；设置了 `EVALUATOR_DATA_DIR` 时继续使用同一绝对路径。新版本运行的工作目录切换到对应版本目录，数据路径单独传入。自定义持久目录不能包含安装目录，也不能位于 `releases/` 或 `.updates/` 内。

完整备份位于 `.updates/backups/<transaction>/data/`，包含加密配置与主密钥，属于私有数据，不能上传发行页。失败恢复会保留失败时的数据目录与匹配备份。采集虚拟环境的符号链接原样复制，不读取系统 Python 链接目标；业务资料若使用其他符号链接，更新会阻止备份，需先人工整理。更新前会检查备份与恢复空间。

新版启动失败时，启动器停止该版本，成对恢复原代码和更新前数据，再检查旧版本启动。进程未确认退出、备份不完整或恢复失败时保持维护状态，保留全部证据，不启动旧代码读取新版数据库。断电恢复依靠持久事务阶段，重启时先处理未完成更新。

手动恢复前必须确认 API 与后台进程均已退出。保留整个安装目录，找到事务记录里的 `previous`、`data`、`backup`，把完整备份恢复到原数据路径，再将版本指针改为对应旧版本；不要仅删除维护锁、清空 `.updates/` 或更换 `master.key` 来绕过恢复检查。需要维护者确认不确定状态后再恢复业务执行。

已有采集虚拟环境且新版采集依赖指纹发生变化时，当前版本会在停机前阻止更新，提示维护采集环境；不会改写正在使用的共享 Python 环境。旧版本、成功备份和失败目录暂不自动清理，需维护者确认后清理。

## 接口与验证边界

所有接口沿用本机 HttpOnly 会话，插件导入 / 报告令牌没有更新权限：

| 接口 | 用途 |
| --- | --- |
| `GET /api/updates` | 当前版本、已检查版本、脱敏更新源和事务进度 |
| `PUT /api/updates/source` | 保存仓库与可选令牌，空令牌保留，`clearToken` 显式清除 |
| `POST /api/updates/check` | 检查并持久保存完整正式发行版信息 |
| `POST /api/updates/install` | 确认下载并安装；阻塞后再次调用表示重新检查安装条件 |
| `POST /api/updates/cancel` | 取消下载、准备或尚未安装的更新 |

下载验证受信仓库、HTTPS、整包与逐文件哈希；令牌只发往对应 GitHub API，跨域附件重定向不携带令牌。更新包拒绝路径越界、Windows 文件别名、符号链接、重复文件、超额解压和测试快照。哈希提供完整性校验，发布来源与仓库权限负责信任，当前没有独立的发行签名机制。
