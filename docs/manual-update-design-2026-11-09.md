# 手动在线更新设计

日期：2026-11-09。状态：设计草案，尚未实现、发布或完成 Windows / macOS 验收。

实施进展：已按此方案加入 GitHub 更新入口、独立启动器和安装事务；具体可用范围、发布方式及待验收项目以 [在线更新说明](manual-updates.md) 为准。实际安装保留原根目录 `.data/` 作为固定数据路径，避免首次接入再迁移一次；启动器协议 1 暂不自更新。Gitee 适配与 Windows 实机验收尚未完成。

## 目标与已确认范围

交付人发布一个版本，同事在平台内检查版本、阅读更新说明，手动确认下载、安装和重启；日常更新无需聊天发送压缩包、手工解压、搬迁数据或执行 Git 命令。

用户确认以 GitHub / Gitee 发布页作为分发来源。首次交付仍需要安装包，用它建立后续可更新的安装结构。第一版提供稳定版更新；后台不自动安装，不因打开页面而中断任务。

## 入口与弹窗

侧栏左上角保留现有 Logo 与“Kooboo 自动化”，名称下增加可点击版本号，例如 `v0.4.0 ↗`。版本号是独立按钮，不嵌套在现有首页链接内；折叠侧栏时在底部提供更新图标，保证仍可访问。系统设置同时提供“检查更新”入口，打开同一个弹窗。

版本号始终可以打开弹窗。已检查到新版时显示一个小圆点，提示信息使用“有新版本”；没有检查成功时只显示当前版本，不能误写为“已是最新”。默认由用户打开弹窗后检查，支持再次手动检查。

弹窗宽约 680px，窄屏使用可滚动布局。标题为“系统更新”，主体只保留：

- 当前版本与最新版本，同一行对照；发布日期跟随最新版本。
- 最新版发布说明，可滚动阅读，提供“查看发布页”。
- 与当前更新相关的进度或问题；有阻碍时直接解释怎样处理。
- 底部“检查更新”和主按钮“下载并更新”。

环境兼容等细节仅在影响更新时显示，例如“需要 Node.js 24 或以上版本”。构建号和排障信息放在可展开区域，正常界面不堆叠技术标签。

首次点击“下载并更新”时，在弹窗内明确提示“安装时将重启平台，配置和任务数据会保留”，通过“确认更新”进入更新流程。已有未保存的表单修改时先处理离开提示。

## 界面状态

| 状态 | 内容与动作 |
| --- | --- |
| 检查中 | 保留当前版本，显示检查进度，禁用重复请求 |
| 已是最新 | 展示最近成功检查时间，可重新检查 |
| 发现新版 | 展示版本对照和发布说明，允许下载 |
| 不能检查 | 在弹窗内说明网络或权限问题，保留重试与发布页入口 |
| 下载 / 准备中 | 显示实际下载字节或具体准备阶段；没有总长度时不编造百分比 |
| 有活动任务 | 展示数量和“查看任务”，已下载内容保留；主按钮改为“重新检查并安装” |
| 安装中 | 展示备份、切换阶段；进入停机切换后禁用取消 |
| 重启中 | 显示“正在重启平台，请稍候”，重连原地址 |
| 更新完成 | 核对服务版本后刷新前端，使用浮动通知提示成功 |
| 更新失败 | 显示失败阶段、当前仍可用的版本和重试 / 恢复入口 |

关闭弹窗不取消已经确认的更新。重新打开页面后从持久状态恢复进度。下载、准备阶段允许明确取消；安装阶段按已记录的事务完成或恢复。安装完成但页面重连超时，只能显示“尚未确认启动结果”，不能直接宣布回退或重复安装。

## 发布与接收

交付人流程：版本号递增 → 测试与构建 → 制作版本包与更新清单 → 上传发布附件 → 最后发布该版本。为常规发布提供一个本地发布命令，后续可接入仓库 CI；发布失败或附件未完整上传的版本不进入可更新列表。

同事流程：点击版本号 → 检查更新 → 阅读说明 → 确认下载并更新 → 等待平台重启 → 继续使用原工作区。

更新源配置包含提供方、仓库地址和访问凭据；由交付包预设，日常使用者无需配置。私有仓库凭据按本机加密配置保存，界面和日志不回显；不将交付人的个人 Token 固化在安装包内。需要在接入时确认实际仓库的公开 / 私有属性与同事的读取授权方式。

优先接入一个实际仓库，保留提供方适配层。GitHub 和 Gitee 的发行查询、附件访问及授权分别实现，不假定两者接口兼容。同一版本同时托管两处时，以一致的发布清单和包哈希识别内容，不在下载中途混用不同来源的文件。

提供方适配层分别查询发行记录和附件。接入时依据所选提供方的官方文档核对当前接口、附件容量限制、授权和下载重定向，并在实际仓库完成集成验证。

## 更新包与版本身份

继续使用现有 `scripts/package-platform.py` 的隔离构建、个人数据排除与逐文件哈希规则，增加更新清单。更新包包含匹配的前后端构建产物、SOP、采集引擎与锁文件；接收端不需要重新编译源码。

更新清单至少记录产品标识、清单协议版本、应用版本、构建提交、发布时间、最低启动器版本、系统 / 架构适用范围、Node / Python 要求、数据迁移版本、附件名、字节大小和 SHA-256。官方自动生成的源码归档不作为可安装更新包。

`package.json`、发布标签、交付清单、前端显示与健康接口采用同一构建版本来源。当前健康接口硬编码的 `0.4.0` 应随实现一并改为读取构建元数据；相同正式版本不可重复发布不同内容。

下载使用受信发布源和 HTTPS，验证大小、整包与逐文件哈希、产品及运行要求。哈希用于确认完整性，发布来源和授权用于确认可信来源，不能把包旁边的哈希当成独立的发布签名。更新说明以转义文本或关闭原始 HTML 的 Markdown 显示。

解压拒绝越界路径、符号链接、重复归一化路径和超额展开体积。下载凭据限定发送给对应提供方的受信接口，跨域重定向不转发 Authorization。暂存、安装、校验都不得读取或覆盖个人密钥。

## 安装结构与启动器

采用固定安装根目录、按版本隔离的应用目录、固定持久数据目录，以及独立于 API 的启动器。示意路径为 `releases/<version-build>/`、`shared/data/` 和 `updates/`；更新事务及暂存文件位于数据备份范围之外。实际指定了 `EVALUATOR_DATA_DIR` 时继续使用该绝对路径。

启动器负责启动 API、等待 API 与 Worker 完整退出、切换版本以及重新启动服务。它在主服务退出后仍存在，不能由即将退出的 API 自己完成后半段更新。更新指针使用跨平台可恢复的文件记录，避免依赖 Windows 符号链接权限；更新操作持有安装级互斥锁，多窗口与多实例不能并行安装。

以后同事始终通过相同启动入口使用平台。新版本运行时，工作目录是该版本根目录，数据路径则显式传入固定位置；本机访问地址仍为 `127.0.0.1:4180`。

Node 和 Python 本体仍属于首次安装前提。更新器可在暂存版本目录内部调用 npm 安装该版本锁定的依赖，按需准备匹配的 Chromium；由更新器展示阶段与错误，同事不用手工运行命令。下载准备尽量在旧服务仍可用时完成，依赖准备失败保留旧服务。

采集 Python 环境目前位于数据目录。第一版若发现新引擎要求变更现有 Python 环境，应在停机前明确阻止此次应用内更新并提供维护说明；不能在旧服务运行时修改共享环境。支持环境自动升级前，须实现独立准备、核验与恢复机制。固定数据路径也避免每次版本切换都因虚拟环境绝对路径变化而重建。

## 安装事务与数据保留

1. 将包下载到暂存区并完成解压、依赖准备、版本要求与磁盘空间检查。需要满足新包、旧包、完整数据备份的空间，空间不足时原服务继续可用。
2. 安装前再次检查活动工作。范围包括生成、评测、AI 跟进、采集、经验复盘、交付、旧评测和仍在写文件的排障导出。发现活动工作时不主动中断、不隐式排队到稍后安装，等同事处理后再次点击安装。
3. 通过可持久化的维护锁关闭新的写入与任务领取，并与 Worker 确认没有新领取或仍持有的执行；这一步需要处理检查与领取之间的竞争。维护锁不能只等同于某一个队列的暂停开关。需要手动中断的任务沿用已有停止确认流程。
4. 完整关闭 API、Worker 与写入任务后，备份整个实际数据目录，包含数据库及 WAL、资料、证据、会话、加密配置与主密钥。备份权限沿用本机私有数据权限，不进入发布包或普通日志。
5. 保存旧版本指针与备份位置，持久记录更新阶段，再切换到准备好的新版本。运行数据路径保持固定，避免边复制业务目录边运行。
6. 新版本在维护锁下进行必要迁移和启动检查。检查目标版本、数据可读性、API、后台执行服务及所需运行组件。启动检查不发送模型请求、不新建站点、不执行真实业务任务；所有任务入口仍受维护锁约束。
7. 检查成功后记录更新完成，解除维护锁并恢复更新前的队列开关。恢复现有任务继续遵循已持久化的检查点、取消确认和未知请求规则，不能因为升级而重投结果不确定的请求。

下载或准备失败时不切换。停机后的失败保留备份、旧版本与事务记录；能确认新版本始终处于维护状态、没有新的业务写入或外部执行时，可成对恢复旧代码与更新前数据。不能只启动旧代码读取已迁移数据库。恢复条件不明或恢复失败时保持维护状态，提供清晰的本机恢复说明，不自动反复重启。

断电或进程中断后，启动器先读取更新事务，确认当前版本、备份和数据阶段，再继续完成或恢复；不能把未完成更新当作正常启动。成功后保留最近可恢复版本与对应备份，清理策略另行明确，不静默删除唯一备份。

## 旧 ZIP 用户的接入

需要一次带启动器的新交付包。已有同事先停止旧服务，将完整实际数据目录接入新安装结构，核对原任务、规则、经验和模型配置；数据改路径时按现有交接约定重建采集虚拟环境。后续更新由平台自行处理，不再反复迁移数据。

开发源码工作区显示“开发环境，请使用仓库工作流更新”；不让在线更新器覆盖开发者的未提交源码。团队同事使用受管理安装包，正式发布拒绝将 `--allow-dirty` 的测试快照作为稳定更新。

## 实施顺序与完成标准

先完成版本元数据、一个实际发布源、入口和检查弹窗；再完成发布命令、受管理安装结构及启动器；最后接通安装事务、重连、失败恢复和旧用户接入。下载按钮只有在完整更新链路可用时才启用，只有检查能力时不能称为已完成在线更新。

针对性测试覆盖版本比较、协议及产品不匹配、授权和重定向、包损坏、越界解压、重复安装、活动工作及领取竞争、数据备份、每个事务阶段中断、迁移失败、代码与数据成对恢复、重连后的版本确认。使用隔离的合成数据验证密钥、规则、历史任务和证据保持一致，不使用开发者个人 `.data/`。

Windows / macOS 都须完成实际安装、更新与恢复验证；静态检查和模拟测试分别记录，不能代替实机结果。界面验收优先由用户手动完成，浏览器控制另需明确许可。

尚待接入信息：仓库地址、优先提供方、公开 / 私有属性及读取授权。现有部署与交接文档只在更新功能实际完成后修改为新流程，避免把草案写成可用能力。
