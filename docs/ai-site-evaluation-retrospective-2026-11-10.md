# AI Site 评测效率与费用复盘

核对时间：2026-11-10 10:22（北京时间）。统计基线来自只读核对账本、事件、配置与源码；后续源码实施见第6节。全过程没有恢复任务、请求真实模型评测、修改生成站、部署或提交代码。四项根任务的优化状态均为 stopped。14:38:41 的预期维护重启不作为事故原因追查。

## 结论

当前主要问题是把独立评测实现成了一个可以长期探索文件、工具、来源和实现的通用 Agent，再叠加全范围复评、恢复和修复循环；确定性事实重复由模型查证，修复后的复评又重复完整审查。预算护栏是辅助措施，不能替代流程提效和达标交付。五个任务并行不会减少每个任务内部的串行模型请求。

已经做过的截图索引、切片、结果骨架、路径修复和响应压缩解决了局部问题，但真实数据尚未证明整体降费。继续恢复历史任务并不是验证优化有效的合适办法，用户停止是合理止损。

## 2. 为什么慢

### 2.1 模型在准备工作中花费了大量轮次

| 评测样本 | 模型请求记录 | 已知费用/元 | 其他观测 |
| --- | ---: | ---: | --- |
| Torque 修复1复评 | 1,328 | 10.3305 | 当前保存14批；累计23次SDK会话启动事件；模型请求时间并集约99.8分钟 |
| Car Dealership 修复1复评 | 691 | 9.0359 | 当前保存7批；累计13次SDK会话启动事件；模型请求时间并集约67.4分钟 |
| Movro 修复2完整复评 | 250 | 2.9030 | 3批；记录评测执行约28.7分钟，模型请求时间并集约25.7分钟，程序取证约0.2分钟 |

会话启动事件包含正常分批、恢复、修正或范围变化，不能全部称作重试。旧任务部分生命周期统计从中途启用，不能把全部请求时间与不完整的阶段计时直接相减，也不能把任务创建至最后事件的跨夜时长当作连续执行时间。Movro 最新完整样本的阶段与请求计时可以用于定位主要瓶颈，但不是与其他站点的等条件性能对比。

对事件中的命令文本按固定规则分类：Torque 修复1复评记录765次文件读取/搜索命令、347次脚本或图像处理命令、59次 validate_result 命令；Car Dealership 相应记录432次文件读取/搜索命令；Movro 最新完整复评仍记录249次文件读取/搜索命令、50次 inspect 查询及42次 browser 命令。

命令事件与模型请求不是一一对应关系：可能并行、一个命令包含多步、事件只保留命令前缀；因此不能按命令比例分摊金额。这些数量足以表明“查找信息、组织文件、核对格式”本身成为了大量工作。评分模型不应该每次重新学习目录结构或发明读取/裁图/组装报告的方法。

### 2.2 五个并发没有消除单任务内部的串行工作

当前实际设置为 generationConcurrency=5、evaluationConcurrency=5，timeoutMinutes=60。不是配置只允许一个评测。每个 Agent 的工具观察与下一轮判断仍有串行依赖，上千次请求自然积累较长时间。

没有本次证据证明 CPU、上游限流或浏览器 networkidle 是主要瓶颈，不应先增加并发或缩短等待来推断提效。

### 2.3 来源发现、实现核对与视觉判断混在每个评测里

评分批次会读取规则、目录、图像索引、来源资料、实现和提交 schema；完整度批次又核实相关事实。程序虽已做截图和索引，但模型仍可继续自由探索并重新读取。

Torque 的冻结清单有17项：同一批37条路径分布于 source-coverage、source-page-inventory、site-pages，并与实体、关系和动态模板检查重叠。不同检查目的确实不同，不能直接删掉；问题在于缺少共享的程序事实表，同一事实反复付费查证。37条路径又全部作为静态 page 分批，动态模板与静态页面的边界不清。

## 3. 为什么贵，以及为什么没有及时停止

### 3.1 长上下文乘以大量请求

Torque 修复1复评的单请求输入中位数约89,126 token；Car Dealership 约99,576；Movro 最新复评约99,026。这里包含缓存输入，不等于每次都新读这么多内容。问题是请求数与上下文规模同时偏大。

局部 JSON 体积压缩只减少其中一部分输入，不能修复大量工具往返和输出成本。Movro 修复1复评151次请求、2.2851元；修复2复评250次请求、2.9030元。两轮条件不同，不能据此精确判定优化变差，但足以说明目前没有实现或验证整体降费。

### 3.2 独立评测缺少请求级累计预算

`server/automation/evaluator.ts` 调用 usageCapture 时没有传 RequestBudgetPolicy；`server/automation/usage-proxy.ts` 只有收到 policy 才创建 RequestBudget。因此评测有账本，没有与规划/跟进相同的累计请求/token入场限制及相同请求循环保护。

`server/automation/worker.ts` 的 timeoutMinutes 限制单次启动，不是同一评测恢复后的累计额度。批次有检查点，但未完成批次重新启动仍可能从准备工作开始。

四个根任务冻结的优化策略均为 targetScore=85、maxRounds=3、maxCostCny=null。限制修复轮数不等于限制一轮内部请求数。即使填写全流程费用上限，`optimizationBudgetReason` 目前也主要在阶段切换处检查；阶段内上千次请求仍需要调用前的预算校验与预占，而不能等阶段结束才发现超支。

### 3.3 不可修复的来源缺口没有独立的停止路径

Carent 最后完整报告 desktop86.4/mobile85.6，但来源全集未闭合，全站完整度未通过。已知39条来源路径能够在目标站对应，并不证明没有未知孤立页。继续改目标站不能消除这一来源未知。

当前流程把质量达标、来源完整和必交付项都用于判断目标是否达到；没有达到就可能进入同一个修复规划分支。应保留严格的全站通过标准，但把目标缺陷、来源限制、平台执行失败分别决定后续动作。不能通过弱化评分或把未知改成通过来节省成本。

### 3.4 额外学习和无改善判断也需要约束

四个工作流合计61条学习运行记录（含失败/排队），经验费用约4.2051元。`experience.ts` 对整份 interruption 序列化后做指纹；时间等易变字段可能使同类中断形成新学习运行。这是明确的重复风险，尚未逐项证明61条中多少条属于重复，不应把全部经验费用称作浪费。

四个根任务没有 autonomy 对象，常规优化路径使用规划模型给出的 progress.improved 更新无改善计数，而非仅依赖宿主验证的改善。即使评分确有上升，也还缺少“增益是否足以支持下一轮成本”的策略。Movro 从69.2/63到75.6/63.4，桌面改善明显，移动仅上升0.4分，不能仅凭 improved=true 无限支持投入。

## 4. 优化方案与优先级

### P0：确定性完整度工作交给程序

程序共享路径、双端取证、证据身份、字段、分页、数量与完整标识的事实结果，模型只做语义、视觉与实际交互判断。数据存储与来源标识必须明确映射；未知时不猜集合、字段或全集。程序事实不自动把缺少语义证据的项目提升为通过。

### P1：修复后进行问题驱动的针对性复评

1. 建立共享事实与证据依赖表；不同指标可以引用同一个程序核验结果，各自保留独立判断，不重复拉同一份后台或来源。
2. 新任务在生成前区分静态页面、动态模板、实体与关系，冻结已知来源范围和限制。来源全集未知仍明确保留未知，但不为此反复修站。当前历史冻结清单不能偷偷缩减。
3. 保留首次完整基线；中间修复优先检查缺陷关联路径、视口及共享组件的影响范围，同时保留全量便宜的路由/数据核验；最终将当前独立复验与证据一致后继承的判断合并，按原完整范围校验，不要求每次再次用AI完整重评。
4. 增量结果复用必须依据当前修订的变更清单与可靠依赖关系。全局CSS、布局或共享模板变动扩大复评范围；依赖不明时保守重测。旧目标截图不能仅因路径相同而证明新修订通过。
5. 同一修订已经证实的来源限制不重复调查；出现新资料、新路径或可靠新证据时才重新开启该项。

### P2：把评分从自由探索改成有界判断

保留当前约定的 Codex SDK。由宿主组织批次输入和工具权限，向模型直接提供完成判断所需的最小材料：固定指标、目标/参考成对截图、路径与视口身份、连续区段映射、已验证的程序事实、必要原文片段及紧凑输出 schema。

评分批次不再拥有默认全目录探索、全量来源重扫和任意临时脚本流程。需要补充信息时，返回结构化“缺少什么证据”的请求，由宿主从限定只读工具取得；补查次数计入批次预算。工具缺口和材料错误先由程序处理，避免让模型试参数、猜字段、裁图和反复组装长文件。

正常评分以每批一次判断调用为设计目标，允许一次有界的字段/证据修正；不把几十次工具轮次当作正常完成条件。涉及实测交互的批次单独制定脚本和预算。直接提供图片的输入能力与提供方用量必须通过真实图片的小范围验证，单元测试不代表这项能力已上线。

程序负责：URL映射、来源身份与路由清单、HTTP及链接结果、实体数量/字段/关系对账、证据哈希/修订/视口归属、字段/schema校验、加权总分、报告差异、预算和停止。HTTP200不代表内容正确。

模型负责：视觉构图、字体/间距/层级、语义对应、交互体验和程序不能可靠判断的问题。程序事实不能自动变成视觉通过，模型也不必重复计算确定性总数。

### P3：约束修复与学习的边际成本

程序先筛出真正能由目标站修复的问题；来源限制、平台错误和预算耗尽进入各自停止/处理路径。修复委托按共享模板或组件归并，不逐页复述同一问题。

无改善判断使用宿主可验证的分数、必过项、缺陷和完整度变化；问题标题消失不自动等于修复。下一轮同时参考剩余预算、严重缺陷和连续改善情况。具体阈值通过后续受控样本定标，不把微小涨分当成收益充分。

经验选择先使用场景/阶段匹配和已有采用结果，必要时才调用模型。对中断复盘使用稳定的故障类型、证据及输入指纹去重，排除时间等易变字段；索引和队列一起迁移。例行维护/取消与同因断流不重复生成昂贵经验，学习也纳入工作流总费用。

### P4：预算只作为辅助保护

以下为后续可选保护方案，本次不通过增加熔断来解决交付效率问题。额度需结合完成验收的实际工作量确定，达到上限只表示未完成，不能作为优化成功。

1. 若启用预算，新评测冻结总费用、请求数、token、累计活动时间预算，并配置批次额度；同一评测恢复累计，同一工作流的多轮评测也受总预算约束。不能通过新建会话、重试、结果修正或学习运行绕过。
2. 每次外部请求前，在同一事务中预占当前请求的最大允许开销，包含缓存/未缓存不确定性、图片输入与输出上限；未知用量保留预占，无法可靠估算时使用保守上界或拒绝调用。只在阶段间比较已经发生的账单不构成费用硬限制。
3. 批次超限保存已完成结果和缺口，停止新模型调用，明确标记未完成；预算停止由程序处理，不再付费调用 Agent 解释或自动恢复。
4. 为最终验收保留预算；修复规划与修复执行不得吃完最后验收额度。额度不足时保留当前站和报告，不能宣称已验收通过。
5. 具体默认金额与请求额度需按范围定标，不能从这四个混合故障/恢复样本拍定统一阈值。界面应在开始前展示额度，而不是执行后才统计超支。

## 5. 如何判断优化真的有效

评测占总成本的比例是报警信号，不能单独作为目标：生成费用上涨也会让该比例“变好”。优先比较相同范围下的一次完整评测费用、请求数、活动时间、覆盖及漏判情况。

后续先做离线、固定输入的对照，不恢复这四个生成站：选取小/中/大三种范围的固定报告与取证，程序测试使用 mock；需要真实模型计费对照时再单独安排有明确预算的小试。保存同一模型/价格时段/输入范围，记录冷启动与缓存条件，不把已复用大量检查点的恢复当作新流程基准。

建议第一轮工程目标为同等覆盖下，模型请求数与已知评测费用至少下降50%，活动时间下降40%；这些是待验证目标，不是已有收益或当前承诺。更优的长期形态应接近“每个语义批次一次判断”，而非从上千次请求稍微下降。

验收还必须满足：重大缺陷识别与证据有效性没有退步；全范围和双端要求没有被静默缩减；网络中断、恢复和格式修正不能把旧证据当作当前证据；不能完成则如实输出部分结果和未验证范围。

Dashboard补充以下信息即可支持决策，无需为流程版本特意做标签：

- 站点完整工作流：首次生成、修复生成、各轮评测、规划、学习和跟进的费用及已知/未知用量。
- 一次评测/一个批次：范围规模、请求数、输入/缓存/输出、费用、取证时间、模型时间、工具时间、等待与恢复次数。
- 有效工作与重复工作：新采/复用证据、通过schema的提交、格式修正、重复取同一事实、同因失败次数。
- 价值：本轮实际解决的严重问题、双端评分变化、未解决来源限制、是否最终通过，避免只显示“运行成功”。
- 趋势：单次任务作为完整样本按开始时间归组，显示样本数及P50/P90；运行中的任务和跨小时未完成样本单独标出。时段实际资源占用可以按区间分摊；一次完整评测耗时不能分到每个跨越小时重复当作一条样本。

## 6. 当前落地边界

运行服务已经包含前序的路径契约、取证索引/连续切片、结果骨架、来源默认预览及部分恢复修复。这些局部改进不等于上述架构方案已实施。

report-comparison、历史委托本地化与报告元数据压缩已在源码中通过针对性检查，但本轮没有重新构建或部署，不能声称正在运行的服务已包含这些新增内容。

本复盘没有修改源码、预算、队列、生成站或任务状态，没有运行付费模型或浏览器验收。下一步应先实现P0及有界评分原型，用受控验收验证后再开放批量运行。

## 证据定位

- `server/automation/evaluator.ts`：usageCapture入口、每批SDK会话、自由工具提示、结果修正与完整度合并。
- `server/automation/usage-proxy.ts`、`request-budget.ts`：可选预算接入、预占、请求计数及未知usage处理。
- `server/automation/template-review.ts`：按视口和交付项分批、清单变化时重新组织、批次检查点。
- `server/automation/template-capture.ts`：来源/目标截图计划、哈希与修订绑定、取证复用。
