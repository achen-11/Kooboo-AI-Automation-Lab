## 职责与归属建议

- 采集 AI 判断来源范围疑点、选择发现和补采策略、按页面类型及异常复核、提交带证据的结论。
- 程序执行批量采集、素材下载、解析提取、计数、身份和关系核对；平台保存状态、证据、版本和用量。
- 采集成果归属来源资料版本，支持后续任务复用；迁移任务固定引用具体版本，不能把共享工作目录变化当成旧版本更新。
- 沿用平台现有本地 AI 执行方式；本轮不指定模型、配置布局、新建独立服务或新的 AI 审核角色。
- 网页、资料与工具返回都是待分析数据，不得修改任务范围、权限、预算或执行约束。

## 输入建议

最低业务输入为来源入口和任务目标；范围沿用用户任务及已确认默认规则，不要求用户先整理 sitemap。

平台同时提供：

1. 语言、域名和全站/有限范围，必须保留排除项的依据；已有全站任务不能自动缩为已发现集合。
2. 已保存资料索引、来源版本、失败项、复核记录和本轮触发原因，允许恢复时从具体缺口继续。
3. 已发生用量、单次执行边界、恢复条件以及用户明确设置的硬限制，具体参数后续确定。累计用量完整保留用于归因和异常识别；软额度和执行分段到限时自动保存进度、安排下一批，不默认终止整个任务。
4. 可用工具及权限、适用经验；读取只给短索引，批量原件由程序处理，AI 按需读取。

## 产出建议

| 产出 | 要点 |
|---|---|
| 资料本体 | 原文、结构化候选记录、图片、附件和路由信息；复用 site-harvest 契约 |
| 来源清单 | URL/记录 ID、发现依据、分类归属、分页与顺序、预期量及其依据、实际采集身份集合 |
| 追溯映射 | 原始响应到提取正文、数据记录及素材的对应；记录采集时间和提取器版本，不以哈希证明完整性 |
| 核验记录 | 程序检查与 AI 复核分别保存；AI 复核含样本、类型覆盖、异常、证据与结论边界 |
| 缺口与恢复记录 | 未解决项、已尝试操作、累计用量、停止原因、下一步及可复用缓存 |

原始缓存可由平台保管而不全部上传 Kooboo，但必须可追溯；下游短索引不能截断或替代必迁内容。

## 交接建议

采集执行结束与 A 段可交接分开保存。执行成功、文件检查成功、no-known-gaps、AI 自述完成均不能单独触发正式迁移。

正常任务自动核对并交接，不增加逐份人工确认。平台应检查：

1. 范围明确且来源覆盖证据适用。沿用 shared/migration.ts 的 sourceCoverage / scopeCoverage；既有全站任务不能静默变成有限范围。明确有限范围可按该范围验收，同时保留全源站未知；改变范围需用户明确决定。
2. 所有范围内必需项具备当前资料版本的证据；已知失败、截断、遗漏、归属不明和关键内容未提取不能被跳过。未适用项必须给出依据。
3. 有来源总数时核对不同记录 ID、分页、关系和实际总数；无总数保留未知，不伪造百分比。没有 sitemap 不自动判失败，但发现停止也不独自证明全集闭合。
4. 程序文件/集合核对通过，AI 复核记录覆盖实际页面类型及异常；保留抽检而非逐页语义证明的边界。原件、提取和派生资料一致，平台核验证据引用而非只信模型状态字段。
5. 交接冻结资料、清单、核验记录的共同版本；下游 B 段不得丢弃来源局限。

业务结果可表述为：可交接、可继续补采、保存结果等待处理或停止。本轮不确定新的代码状态枚举。

有可补缺口时定向补采；临时故障按策略退避并自动恢复；停滞时先限次诊断和调整。来源无法补齐、范围冲突、无可行下一步、循环熔断、用户取消或明确硬限制触发时保存结果并停止相关自动执行。软额度或单次执行时限不直接等于任务结束。停止不代表原站完整。后续是否允许带缺口试迁移需沿用明确授权，不能默认当正式迁移放行。

## B 段后续反馈

B 段发现来源遗漏时，回到 A 段定向续采并形成新资料/清单版本，保留旧报告与旧基线；只回归新增项及受影响范围，未知影响则扩大检查。目标站缺陷仍在 B 段修复，不启动重复全站采集。

用户已确认原则：第二轮及以后的工作必须有明确任务目标，不能用“继续完善网站”作为完整委托。该原则用于补采、修复和复评；首次任务也应有目标与范围。

以下字段是对原则的落实建议，具体代码契约尚未实施：

| 内容 | 要求 |
|---|---|
| 问题与依据 | 引用具体 checklist 条目、差异、URL/记录 ID 和适用于当前版本的证据；原因尚未确定时保留为假设 |
| 本轮目标 | 说明预期补齐什么、修复什么或查明什么，允许以取得证据或确认原因作为诊断目标 |
| 操作与影响范围 | 指定批次、栏目、模板或资料类型，以及必须回归的依赖范围 |
| 验收依据 | 指定需要重新取得的内容、集合、响应、截图或业务证据；不能仅以自述完成或总分变化验收 |
| 执行边界与防循环条件 | 记录本轮操作范围、恢复点及验证条件，沿用累计用量和失败历史；没有新依据不得原样重复委托 |

这些任务由平台与跟进 AI 根据清单差异及证据形成，不要求用户逐轮编写提示词。范围冲突或无法补齐的来源按既有等待处理规则处理。

每轮结束对照本轮目标记录实际变化、已解决项、新证据、未解决项及消耗；补证据不冒充修站成功，错误数量下降也不能掩盖新增缺口。没有收益时判断是否有新证据支持改变策略；不具备时停止自动重复。

## 下一步讨论：缺口到任务，以及继续与停止

本节缺口路由、任务形成和进展分类已获用户基本认可，尚未实施。用户进一步纠正了预算优先停止的方向，以下以最新修订为准。已只读核对现有 followup.ts / optimization.ts：修复规划要求实际观察、具体消息、适用图片和改善分析，当前质量优化仍有累计预算、最多轮数及连续两轮无改善停止；尚不能据此声称采集任务或新的自动恢复策略已接入。

### 形成任务

跟进 AI 在阶段完成、阻塞或异常时读取当前版本的清单、缺口、必要证据索引和上一轮结果，判断阶段级下一步。采集 AI 在已下发目标和单次执行边界内完成发现、补采与复核；分段后由平台接续，常规请求重试由程序执行，不为每个网络请求额外启动跟进 AI。

缺口先按证据归属：

- 来源未发现、未采集、原文提取不足或必要素材缺失：A 段采集任务。
- 资料齐而目标实体、关系、正文、模板或路由有差异：B 段修复任务。
- 证据不适用、检查器不识别版式、清单定义错误：先核验或诊断，不能据此把站点判坏。修正规则和基线必须保留版本、依据及原必交付范围；不能以检查器维护为由删减交付要求。
- 范围冲突、权限或来源长期不可用：记录阻塞及解除条件，沿用既有等待处理流程。

原因尚未确认时提交有界诊断任务，目标是查明可证实的原因；原因不得伪装成事实。按共同原因合并问题，先处理阻断交接的上游依赖和严重缺陷；批次保留全部条目 ID、URL/实体集合及未处理尾项。不能机械地每 URL 发一轮 AI 请求，也不能把所有问题塞进一个无界委托。

平台校验任务是否引用当前适用版本及实际证据、必填目标/验收是否齐备、是否重复无变化的既有操作、原执行是否已结束及防循环/明确硬限制是否触发；语义可行性仍需带证据的 AI 判断，不声称程序能完全判定。

### 验收与进展

完成一项任务后，先针对目标执行程序核对，再按需要取得语义、视觉或业务证据；覆盖受影响范围，影响未知时扩大检查。阶段正式放行仍按全部必需项判断，局部通过不等于整体完成。这个局部核验策略为讨论建议，当前既有优化流程仍会自动进入正式独立复评。

分别记录：

- 交付进展：原有缺失或错误已由适用证据确认解决，必要回归通过。
- 核验进展：补足关键证据、确认原因或排除会影响下一步的假设；不当作内容已修复。
- 新增发现：新发现的遗漏、目标回归或来源变化单列，不能用总条数增减替代上述分类。
- 无进展：重复读取、原样重试、自述完成、修改问题文案或降低预期，不构成改善。

对比须使用相同资料/清单口径；资料版本或来源范围扩展时单列新增项。例如原10项解决3项，新发现5项，当前12项：应分别记录原问题解决3项与新增5项，不能只看10→12就判原修复无效，也不能忽略新增问题宣布可交接。

### 决定下一步

| 情况 | 建议动作 |
|---|---|
| 当前阶段全部必需项有适用通过证据 | 进入下一阶段，保留版本与来源局限 |
| 仍有缺口，已有进展并有明确下一目标 | 自动继续；单次额度到限则保存进度后接续，不因任务已执行较多轮而默认停机 |
| 未达原目标，但有证据支持不同的可行策略 | 形成有界诊断或调整方案，保留累计用量和失败历史，诊断次数受防循环策略约束 |
| 同一缺口、相同方法、输入无实质变化 | 不再原样派发，保存原因并停止自动重复 |
| 有新增严重回归 | 优先查证和处理；无法形成可信修复任务则停止，不自动推定可回滚 |
| 临时网络、限流或服务故障 | 保存进度、退避并由平台调度自动恢复；恢复前核对原执行，避免重复投递 |
| 外部条件需要用户提供来源或明确范围 | 保存证据及解除条件，等待处理；条件未改变不反复启动模型 |
| 循环或异常消耗达到兜底条件、用户明确硬限制触发或用户取消 | 停止相关付费执行并持久保存结果；其他无依赖任务可继续 |

当前代码的“连续两轮修复无实质改善停止”保留为现状记录；新设计建议先将连续无进展转为诊断、调整策略的触发信号，经过有限尝试仍无可行路径或出现循环才熔断。A/B 各阶段的观察窗口和阈值待定，当前代码没有因此获得自动放宽。真实核验进展单独记录，不伪装为站点修复；失败策略和累计消耗跨角色、跨批次保留。一次有意义的诊断不能成为无限延长流程的理由。

### 完成优先与防循环兜底（最新修订）

累计记账与强制停止分别处理。成本、token 和请求数持续记录，用于优化、定位异常及用户查看；默认不因达到一般软预算而打断仍在有效推进的无人托管任务。

| 边界 | 建议行为 |
|---|---|
| 单次模型、工具或批次的时间/请求/上下文边界 | 本次执行有界，保存可靠检查点后自动接续；不清空累计账本与失败历史 |
| 软预算、规模预估或阶段轮数预期 | 作为观测和策略调整信号，优先复用缓存、压缩上下文、拆分有目标的批次，不逐次要求用户批准续额 |
| 用户明确配置的硬费用或其他硬限制 | 必须遵守，不能以无人托管为由自动越过；缺少必要计量导致无法确认硬限制时按硬约束处理 |
| 无限循环与异常消耗兜底 | 按同一缺口的重复操作、失败策略回转、长期无可验证进展和异常请求增长判断，触发时熔断受阻环节 |

防循环判断不能只信 AI 宣称“有新策略”：需要记录实际输入/方法变化、要验证的假设以及预期取得的证据；相同操作改写措辞、角色切换、分批或反复恢复不能抹掉历史。原样重试仅限适用的临时只读故障，写入/投递结果不确定仍必须先核对。

系统可自动恢复的技术问题优先恢复；只有需要新增来源、范围决定、权限变化、用户硬限制处理，或有限诊断仍无路可走时才等待用户。被阻塞环节的停止不冒充任务完成，也不无故阻断其他独立工作。

## 下一步讨论：检查点、自动接续与防循环执行机制

本节为方案建议。只读核对确认：site-harvest 的 fetch 阶段保存状态、复用原始文件，恢复时从保存 HTML 重新展开遗漏链接；平台已有 worker/recover 机制与生成投递回执，结果不确定时不会直接重发。统一采集任务检查点、自动分段接续及下述目标级防循环尚未实现，不以这些基础能力冒充整条链已跑通。

### 用目标、阶段和批次区分执行结束

- 整体任务：对应用户要求与交付范围，保持连续身份和完整历史。
- 阶段/具体目标：如发现产品栏目全集、补齐某类正文提取、核对图片附件；具有独立完成条件和依赖。
- 执行批次：模型或工具的一次有界工作；批次结束、上下文接近上限或达到单次时限，仅表示需要保存和接续，不默认终止整体任务。

每批必须对应具体目标和明确待处理集合。批次大小按页面体积、类型和工具限制调整，不能仅凭固定“每批 N 页”判进展或完成。

### 平台保存的恢复依据

| 检查点内容 | 用途 |
|---|---|
| 任务、目标、来源/资料/清单版本及范围 | 防止恢复时混用资料或改动原始要求 |
| 待处理、已采、已提取、已核验的不同集合 | 避免把抓取成功当成资料通过；只重新处理失效步骤 |
| 当前操作、执行身份、原投递ID或回执 | 恢复前判断操作是否仍在运行、是否实际生效 |
| 原件/产物路径、校验信息与验证证据 | 核对真实文件，不能只相信模型摘要或数据库完成标记 |
| 缺口、已尝试策略、实际输入变化与结果 | 防止跨角色、跨会话、跨批次重复失败路径 |
| 下次执行时间、阻塞原因、累计用量、取消标记 | 重启后可恢复调度，明确取消的任务不得自动重启 |

关键操作开始前记录目标与操作身份，取得结果后及时保存产物和检查结果。状态记录与文件写入不能笼统视作同一事务；恢复时校验文件和引用，部分写入或缺失文件仅标记未完成并修复对应步骤。保存原件、完成提取、内容核验通过是不同检查点。

模型会话不是恢复的唯一载体。上下文过大或会话失效时，可在平台确认当前执行已结束、必要文件和记录已保存后创建新的本地采集会话，提供目标、短索引和剩余项，按需读取证据。不能因此另建目标站、重发结果不明的写入，或清空原任务尝试历史。Kooboo 原站/原会话的恢复仍按当前投递和身份规则处理，本节不授权无依据更换其会话。

### 自动接续和重启恢复

1. 批次完成但目标未完成：核对产物与剩余项后自动排队下一批，正常情况下无需用户续额或点击恢复。
2. 临时故障：持久保存下次执行时间，退避后由平台调度重试；等待不占用模型推理和活跃工作名额。请求频率和同类故障仍有边界，不能无限高频重试。
3. 服务重启：读取检查点，先核对原执行，再恢复到第一个未完成的具体步骤。同一可变资料工作区/目标的写入保持互斥，避免两个执行器同时恢复同一批。
4. 原执行仍在运行：继续观测原执行，不发起第二份。无法确认是否已结束或写入是否生效时先核对回执、产物或目标；在核对边界内仍无法确认才保留阻塞。
5. 校验缓存失效：按原件、提取器或规则变化重新处理受影响步骤；来源发生变化时保存新版本，旧基线和旧报告保持不变。
6. 用户取消：持久化取消意图并核对在途执行的停止状态，不能把取消当成可自动恢复的临时异常。

### 防循环以同一目标为单位

不以整体任务总轮数限制正常批次，也不因为拆了更多批就认定空转。记录同一目标下实际输入、方法、证据变化、失败原因与验证结果，跨角色和重启保留。

- 同样输入与方法的失败操作不原样派发；适用的临时只读故障可退避重试，次数和恢复观察有边界。
- 同一目标持续无可验证进展时触发诊断，优先程序定位；需要语义判断时再调用跟进 AI。
- 换策略需说明与旧策略的实际差异、证据依据及可验证的预期结果。A→B→A 的回转若输入未发生实质变化，应识别为重复路径。
- 同一目标的诊断和替代策略尝试有限。一次证据进展可帮助选择下一步，但不自动证明问题解决，也不无条件恢复整套失败尝试额度。
- 未知项增加应区分真实新发现与改名重建缺口；相同问题换ID、换版本号但内容未变，不得规避防循环记录。
- 无可信新路径或循环达到阈值时暂停受阻目标，记录所需条件；不依赖它的任务可以继续。全部必需依赖未通过时仍不能宣称整体完成。

诊断触发窗口、退避间隔、替代策略次数和异常消耗阈值在实施时集中定义默认值，当前不新增未经确认的固定次数。兜底不应仅靠 AI 自报进展；宿主检查可确定的产物、集合差异和实际动作变化。

### AI 看到的工具

| 工具功能 | AI 提供的内容 | 平台返回的内容 |
|---|---|---|
| 查询任务与资料索引 | 任务身份、栏目或状态筛选、分页游标 | 范围、当前版本、批次进展及缺口短索引 |

| 核对清单与缺口 | 当前资料版本、核验范围 | 文件、集合、引用及关系的核验结果和证据引用 |

批次操作涵盖抓取、提取、素材下载与重提取，由平台映射到引擎阶段；正常全量处理交给程序，AI 重点处理类型代表样本、异常和无法机械判定的问题。AI 不自行拼接 shell 命令、不选择任意本机路径；范围、已登记对象、参数和依赖由平台检查。需要新解析策略时，按可维护扩展流程实现，不把临时任意脚本执行作为默认工具。

### 调用、证据和上下文

1. 平台先持久化操作身份、输入版本、具体目标及对象集合，再启动 Python 阶段。长任务先返回操作身份，后续查询状态；查询结果不触发重复启动，恢复核对沿用前文规则。
2. 原始响应、完整正文、图片和详细日志保存在平台管理的资料目录。工具默认返回短摘要、计数、缺口和引用，详细集合可分页读取；不得静默截断必需项或将摘要用作唯一迁移正文。
3. AI 的抽检从短索引选取代表类型和异常，再按证据身份读取原件及提取结果。正文大小超过单次读取边界时明确分段及后续游标，不能把首段当作完整内容。
4. 平台校验结构化执行结果、产物存在及版本、引用与本轮对象对应关系；退出码为零只是步骤执行结果，不证明语义内容正确或来源完整。检查器不足须形成核验缺口，不能转成通过。
5. AI 提交含证据的复核记录与下一步建议；平台结合程序核验、适用范围和版本检查 A 段交接条件。AI 自述完成或工具全部成功均不能独自放行。

### 定向补采示例（虚构）

某栏目预期 120 个不同记录 ID，已采 119 条。下一轮任务应明确定位缺少的 ID 或分页，并只补采相关对象；返回新增项、仍缺项及证据引用。若失败页保存的原件已包含缺少记录，则先修提取并复用原件。需要回归对应栏目身份、分页和关系，避免重复采集全部资料；范围或影响未知时先诊断，再决定是否扩大。

此处减少的是模型反复读取原件和重复执行的消耗；不承诺 AI 完全不读正文，也不以限制上下文为理由删减完整资料。

### site-harvest 的实际组成及通用边界

- harvest.py / cli.py：命令入口、范围和阶段编排。
- discover.py：语言及域名范围、sitemap、导航、普通链接、分页与frame入口发现。
- net.py / fetch.py：HTTP请求、编码处理、跳转、缓存、并发抓取、状态及续采；浏览器模式另有系统Chrome调用。
- extract.py：启发式正文选择、结构化段落/表格、图片/链接、SEO、表单及交互线索、fullText证据。
- assets.py：图片与附件发现计划、下载、归账和文件类型检查。
- dataset.py：按重复URL和内容形状生成候选记录组、索引、CSV与分片；属于派生资料。
- render.py：输出逐页Markdown、路由及SEO清单、资料包入口。
- completeness.py / verify.py：已发现对象的失败、缺口和待复核，文件、引用及分片计数等检查。

这是面向公开网站内容迁移、输出Kooboo资料包的通用工具集合。源码未发现按manwei域名生效的分支；dataset.py一处注释使用漫威站点名作例子，实际逻辑读取site_name参数。它可能吸收了案例经验，但不能据此称为manwei专用或已验证任意网站都适用。

平台server/automation/migration-adapters/manwei-saved.ts则明确是案例专用适配器：识别特定域名、分类路径和已存页面版式，用保存证据构造迁移对账输入；不能将它当成通用发现能力或来源全集证明。

通用规则包含假设：例如正文选择基于文本量和链接密度；反复出现的内容可能被派生记录归为公共内容。dataset.py的候选记录summary限制500字符，links只取前20条。原始页面、fullText和派生记录必须分开核对，不能以候选记录本身作为无损迁移的唯一依据。脚本不能自动穷举点击、滚动或API后的数据，PDF正文及图片文字也不自动提取。

### 正确性保障建议

1. 固定样本与独立预期：保存可复用原始响应，人工或可审查依据标注必含内容、身份、分页、素材和应报告的异常；预期不得由被测解析器重新生成。跨模板、编码、表格、动态入口和失败场景测试，同时保留正常页面防止修复回归。
2. 每次任务核对：平台检查独立产物、引用、身份及计数；来源总量有依据时对账，无依据保留未知。增加对原件、fullText、逐页资料及候选记录的差异检查；AI按页面类型及异常复核，抽检不冒充逐页语义证明。
3. 发布与影响追溯：引擎、站点规则和核验器各自版本化。缺陷按受影响类型与版本追溯历史资料；必要时把相关交接结论标为需重新核验，并定向重提取或补采。保留旧资料版本与报告，后续形成新版本。
4. 自检不能独自背书：发现程序和核验器可能共享盲区，不以verify成功或AI自述解决为最终依据；核验器报错属于检查未完成，不能视为无缺口。修复解析器时不得靠放宽预期或关闭核验来达标。

### 故障处置与权限建议

| 情况 | 默认处理 |

| 共享引擎或核验器缺陷 | 形成含原件、预期、实际、版本和影响范围的可复现缺陷，进入隔离修复与回归；运行中的稳定核心不直接覆盖 |
| 无可行修复或进入循环 | 暂停受影响环节并记录所需条件；无依赖工作继续，相关资料不能按完整放行 |

建议权限分层：采集AI可读证据和日志、调用工具、调整受控参数，并可在声明范围内生成版本化的站点解析规则候选。选择器、字段映射和分页规则等必须经过平台校验；不能借规则重定义必迁范围、忽略失败或放宽完整性标准。当前脚本尚无统一站点规则接口，需实施后才有此能力。

采集AI可以诊断代码问题、提出补丁；首版不默认授予改写运行中的共享引擎、安装依赖、修改核验标准或自我发布的权限。需要代码修复时，可交由开发流程在隔离副本中应用候选补丁，复现、回归、检查影响后发布新版本；是否开放自动代码修复和发布，需单独确定策略，而不是默认每次都人工确认。此处不增加新的常驻AI角色。

任务级规则在可核对的条件内可以验证后自动采用，以保留无人托管体验；共享代码发布与跨任务影响处理另行设计。无论谁提出修复，均不能同时自行改掉验收依据来制造通过。修复后的任务从可靠检查点继续，并重新核验受影响资料。

## 下一步讨论：站点规则的内容、验证与采用

状态：用户已基本认可本节站点规则方案，尚未实施，并进一步明确无人值守、减少人工介入及质量保障的总体设计原则。具体接口与阈值未定；后续自动恢复建议见下节。本节用于落实受控站点规则权限，不新增任意脚本执行入口，不修改设置页。

### 首版规则允许表达什么

规则是由固定引擎解释的结构化配置。首版优先表达既有能力的站点差异：

| 内容 | 可表达的差异 | 必须保留的边界 |
|---|---|---|
| 适用对象 | 来源主机、语言、URL模板、页面类型和可识别结构特征 | 同一域名不等于所有页面同一模板；多个规则冲突或特征不匹配时报告待诊断，不静默选用 |
| 正文与字段 | 正文容器、标题/日期/规格等字段位置及已有提取方式 | 必迁内容不因选择器变窄而自动消失；原件及逐页证据保留 |
| 发现与分页 | 已存在的列表链接、下一页位置、总数/页数声明的位置 | 只沿真实发现的入口与语义推进，不凭空枚举记录ID；未经支持的交互/API采集不能伪装成已完成 |
| 素材与关系 | 现有图片/附件属性、分类与详情对应位置 | 保留来源URL、记录身份和归属证据，不通过忽略失败减少缺口 |

规则不负责改任务范围、重写来源身份、降低核验标准或改变共享引擎代码。需要新的操作能力时形成可复现缺陷或扩展需求，进入前节的开发与发布流程。未识别页面保留待处理，不因没有匹配规则而排除。

### 候选规则必须附带什么

每个候选保存：所解决的问题及证据、适用页面类型与对象、原规则版本和候选版本、验证样本身份、独立预期、预计影响范围。样本预期可来自已有人工标注，或采集AI在查看原件后提出并固定的证据化判断；后者明确标为AI复核，不能冒充人工金标准，也不能在试跑后跟随新结果改预期来过关。

例如正文容器规则的预期应具体到某段必含正文、表格内容或附件链接，而非只有“提取字符更多”或“评分上升”。分页规则的预期应包括真实下一页和已知记录身份；总数未知仍保留未知，不以试跑发现量充当来源总量。

### 验证和采用流程

1. 使用已保存原件在独立候选输出目录试跑，稳定结果和冻结版本保持可追溯。新增网络请求只用于确认缺少的原件，不因改正文规则重新全站抓取。
2. 比较失败样本与已正常样本，至少覆盖所声明的页面类型及已知结构变体；保留未用于调规则的回归样本，实际数量按类型及异常决定，不以固定抽取几页代替覆盖。
3. 平台执行产物契约、引用、身份、计数和必含内容检查；采集AI对照原件复核语义。候选规则不得修改这些既有验收依据。检查器不足、证据不够或规则冲突时不自动采用，保留核验缺口。
4. 在适用类型的验证依据充分、原问题得到解决且没有新增未解释退步时，可自动采用到当前任务的声明范围；无需逐次人工批准。样本验证只支持该规则在声明范围内试用，不证明全站提取已正确。
5. 采用后，按该规则的影响范围重提取和重新核验；单独保存新的执行及规则版本。只有共同版本下的A段交接条件满足后，才冻结新的正式资料版本。
6. 出现新退步时停止该规则的继续采用，保留候选产物与差异。可恢复到此前可用版本继续无依赖工作；此前版本已知错误的对象仍保留缺口，不能因回退而标为已解决。按前节原则有限诊断、换策略或升级工具缺陷。

### 规则复用与经验沉淀

当前任务验证通过的规则先归当前来源与明确模板，记录其证据、适用范围和局限。可提炼为经验库中的候选方法；新站只有在特征匹配并完成本次样本验证后才采用，不能因为两个站都使用.aspx或相似URL就直接共用。

若未来要把规则升级为通用引擎默认行为，需增加跨站/跨模板回归并经过共享代码发布流程。工具修复、规则生效和本次资料完整性分别记录，不能相互替代。

### 示例（虚构）

产品详情正文在页面侧栏之后，通用选择器漏掉规格表。采集AI从原件定位正文及规格表，提出只适用于已识别产品详情模板的容器规则；用失败页、正常详情页及其他已知详情变体验证，同时确认栏目页不被误匹配。通过后自动重提取受影响详情，核对正文、规格与附件。若新规则遗漏附件，保留新旧差异并拒绝或撤回采用，任务仍记有未解决项。原件可复用时无需重新抓取这些详情页。

## 无人值守优先：从异常到自动恢复的闭环

状态：用户明确了本节总体设计原则，随后接受首版任务内隔离代码修复及验证后自动采用，要求先评审完整设计；尚未实施。本节保留当时讨论过程，最新整合范围见文首完整设计v1。

### 将处理责任留在平台内

异常形成有目标的恢复任务，由平台持久化并继续调度；“已报错”“已生成缺陷单”或“已提出补丁”均不代表已完成跟进。记录问题之后要继续安排诊断、可用替代方法、验证、恢复原任务及修复结果追踪，不要求用户重新输入“继续”。无需为此增加新的常驻AI角色。

质量条件、用户已授权范围与硬限制保持明确；在这些条件内，应优先自动调整执行方法、批次和任务内规则。已知漏项、核验未完成及未知总量必须保留，不能以任务持续执行为理由将它们标为交付通过。软额度和单次执行时间只触发保存与接续；既有完成优先和防循环原则保持不变。

### 自动恢复的层次

| 层次 | 默认动作 | 继续任务的依据 |
|---|---|---|
| 执行恢复 | 超时退避、阶段重试、检查点接续；依赖缺失走受管理组件自检与修复 | 先核对原执行与产物，避免未知操作重复投递；保留已有成功结果 |
| 站点适配 | 诊断页面差异、调整受控规则、重新试跑 | 独立证据预期、正常样本回归及受影响资料核验 |
| 执行策略替代 | 调整批次、发现顺序、可用提取方法；使用已授权的公开入口或浏览器能力 | 同一业务目标与范围不变；没有授权或能力时不得自行越界 |
| 工具修复 | 条件允许时，在隔离副本中生成和验证候选补丁或任务专用扩展 | 受控能力、固定验收依据、回归及可回退，采用具体版本；首版是否支持需实施前确定 |
| 暂不可解除 | 保存阻塞条件与下次检查计划，继续无依赖工作 | 临时条件变化后自动恢复；同一无效路径不无限重试 |

任务级代码修复是对前面权限讨论的进一步建议，不等于开放任意shell、联网、依赖安装或平台自身写权限。若引入此能力，由平台提供可写隔离副本、受限执行器及允许的模块/工具边界；检查器、固定验收预期和任务范围仍由平台控制。验证通过可按预先规定策略采用到当前任务的引擎版本，避免每次都等待人工审批；向所有任务发布共享默认版本仍走独立发布流程。

若首版未实现隔离代码修复能力，必须明确这项能力缺口；常规恢复路径用尽后保留阻塞，不能以一张缺陷单宣称已经具备无人值守自修复。具体自动发布策略不在本轮假定已确认。

### 何时才请求人工

优先区分可由系统补足的执行问题与只能由用户提供的条件。以下情形才升级为具体请求：

- 需要尚未提供的访问权限、登录状态或真实来源资料。
- 目标、范围或取舍存在无法由现有指令确定的业务冲突，例如必须决定是否改变必迁范围。
- 下一步超出已授权能力、会改变共享运行环境或涉及未授权且难以回退的动作。
- 有证据的自动恢复与有限换策均未解决，且没有新的可行路径，需要人工提供信息或解除条件。

请求应说明已完成工作、阻塞证据、已尝试方法、所需最小动作和继续入口。不得把普通低分、一次错误、一次批次结束或软额度到限默认转成人工请求。人工请求只挂起相关依赖；若条件会变化，仍保存适度复查计划。用户取消、明确硬限制或循环/异常消耗兜底触发后，按相应停止规则处理，不能通过自动换任务绕过。

### 容错与交付质量的验收建议

把“遇到故障后能否自行恢复”列为独立于正常采集的交付验收项，首版至少验证以下场景：

1. 请求暂时失败后，保留成功对象，退避重试并核验补齐项；不要求人工重新发起。
2. 执行中服务重启，从可靠检查点接续，核对不确定执行，避免重复采集或投递。
3. 页面模板变化导致正文或规格遗漏，能发现异常、形成明确修复目标、试跑规则并重核受影响资料。
4. 候选修复引入新遗漏时拒绝或撤回采用，保留原问题与新差异；不能假通过交接。
5. 相同失败反复出现或策略回转时，有限诊断、换策并停止循环，保留成果与下一步条件。
6. 确实需要外部条件时，只请求最小必要输入；条件补足后按保存的目标继续，不重新全站开始。

离线故障注入、真实来源采集、模型实际规划、双平台运行和浏览器行为分别记录验证结果，不能相互代替。以上尚未执行或实现，不宣称已具备这些恢复能力。

某产品栏目声明 120 条，采得 119 个不同 ID，一页失败：本轮采集结束，但资料不能按完整栏目交接。程序保存缺少页和已有 119 条，采集 AI 判断可补方式；补采成功并完成对应核验后形成新版本。暂时失败则退避后自动恢复；403 持续且可用方法均失败时保留缺口并说明所需来源，不重读全部 119 条，也不把预期总量改为 119。软额度到限不直接结束任务，用户明确设置的硬限制仍然遵守。
