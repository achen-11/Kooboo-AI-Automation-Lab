## 已安装的改进

- 已确认停止的模板评测直接恢复执行器，不再先让恢复 AI 判断是否 retry。保持原任务、原站、固定输入和规则、累计用量与未知预占。
- 每个批次生成 `review-input.json`，按本批路径和视口定位原图；长图由程序连续切片并登记来源哈希和区域，避免模型反复查找命令、写裁图脚本。原始证据、完整范围及原有校验仍保留；切片不直接产生分数。
- 生成 `review-result-template.json`，程序列出本批全部指标、视口与交付项的未验证字段骨架。模型独立填写判断，再由既有 nonce 文件、schema、证据归属和全范围校验器验收；不会从默认骨架生成通过结论。
- 跟进的工具观察和 `task.json` 使用相同紧凑上下文：不重复携带完整优化 SOP、旧修复委托和旧行动正文，保留原站身份、修订、状态、轮次进展与当前问题。持久化原记录保持完整。四项实测 JSON 字节数减少 57%–68%，这是上下文体积收益，并非费用等比例下降的承诺。
- 修复分析的图片预检提前到经验选择和尝试计数之前。确定性的缺图直接停止，不空转消耗 5 次恢复机会。
- 对历史已耗尽的前置尝试，只有当前窗口 token 为零、没有 SDK 会话、当前预算账户没有任何请求、窗口内没有跟进 usage，且缺图已实际补齐时，才能纠正尝试次数。历史费用、时间、请求预占和真实模型额度不变；早先其他阶段的请求不再误阻止此类纠正。
- 规划图片输入与选择器统一为 16 MiB 上限，修正先选中双端图片、发送时却因另一个 6 MiB 限制静默漏掉桌面参考图的问题。已有会话中的图片继续复用。

## 跟进时确认的路径契约问题

Torque Cars 的冻结静态页面清单使用 `https://torquecars.framer.website/...` 完整来源 URL。原程序对 target 也直接使用该 URL，再按目标域名拒绝外链，导致计划中仅有 2 个目标入口截图槽、74 个来源截图槽，以及 82 条待核实提示。模型因此不得不逐页补取目标截图。原完整度校验又把源站 origin 当作目标路径身份，即使模型补齐目标截图，仍无法据此认可源站绝对 URL 的静态页面项。这是平台契约缺陷，不能靠修站或降低标准消除。

隔离副本中的修复：仅把明确固定参考站 origin 的 URL 映射为相同 pathname 和 query 的目标路径；保留第三方域名拒绝、登录信息拒绝、查询参数身份及每路径 PC/mobile 实图要求。程序取证与最终完整度校验使用同一映射，冻结清单原件和数据标识不变。仅作废受此映射影响的页面/模板批次，复用独立评分检查点；静态分批不再附带其他批次的 expectedKeys 和 samples。校验失败明确指出交付项与缺失路径。另修正图片辅助索引原先只读取目标 URL 观察、漏列已通过校验的参考图片的问题。

## 新确认的预算缺口与下一步优先级

独立评测的 `usageCapture(task.id, 'evaluation', ...)` 未传入 `RequestBudgetPolicy`，因此有逐请求账本，却没有跟进/规划相同的累计请求护栏。60分钟执行时限只限制单次启动，人工恢复仍会累计更多请求。Torque 全站两个评测合计已超过1,100条账本请求；不能以缓存命中率高为理由忽略重复工具轮次和输出成本。本轮未在执行中途修改已有任务预算。

优先顺序：

1. 给新评测冻结明确的总请求/费用预算，并细分批次预算；恢复继续累计，达到上限保存检查点、停止新请求并显示明确原因。不能让页面仍显示执行中而后台无限恢复。
2. 将来源范围缺口与目标站缺陷分开：来源未提供完整清单、未知孤立页面无法通过修站消除，分数已达标时不要为了同一个来源限制继续改站或付费重评。已知页面仍需保留独立验收，不能把来源缺口改写为通过。
3. 修复分析预先提供程序计算的分数、必过项、已解决/新增问题和完整度差异，模型核对必要截图后只决定有证据的修复动作；避免重新研读两份完整报告及历史事件来计算已知差异。
4. 对同一输入/修订/失败原因的经验复盘建立稳定指纹，减少维护重启和同类断流导致的重复学习；索引升级与队列去重必须一起处理，避免新键导致每秒反复读取大任务。
5. 按模板共享结构分配语义检查与全量程序核验：程序仍验证全量路由、字段和归属，动态模板的视觉检查覆盖声明的样本/边界。不得未经重新确认冻结范围就跳过原清单中的静态页面，也不能把HTTP200当成内容正确。
